# Task 1
- '/31'의 경우 두 엔드포인트 모두 사용 가능하며, '/32'의 경우 단일 주소만을 사용 가능하다. 3번째 반환 값은 항상 호스트 비트가 모두 1인 주소 ('/31'의 상위 엔드포인트, '/32'의 호스트 자체)이며, 이 두 경우 별도의 지향성 브로드캐스트 주소로 취급되지 않는다.
- 10.20.30.70 은 '10.0.0.0/8', '10.20.0.0/16', '10.20.30.0/24', '10.20.30.64/26에 해당하며, 기본 경로인 0.0.0.0/0에도 해당한다. 최장 프리픽스 일치 규칙에 따라 가장 긴 프리픽스인 /26이 선택되므로, 다음 홉은 lab-rack-2가 된다.
- 동일한 프리픽스가 서로 다른 다음 홉과 함께 중복 등록된 경우, 먼저 추가된 엔트리가 우선한다. 조회 과정에서는 현재 선택된 경로보다 엄격하게 더 긴 프리픽스가 발견 될 때만 선택 결과가 변경되기 때문이다. 한편, 프리픽스 길이가 같더라도 서로 다른 네트워크를 나타내는 엔트리들은 유효하며, 그러한 서로 다른 네트워크들이 동일한 목적지에 동시에 일치할 수는 없다.

# Task 2

- 측정 중 별도의 VPN이나 Proxy를 사용하지 아니하였다. 모바일 핫스팟에서 사용된 사설 IPv4 주소 10.188.69.162는 외부에서 관측된 공인 IPv4 주소 163.152.233.30과 달랐고, 이는 두 네트워크 각각에 최소 한 계층 이상의 NAT가 존재함을 의미한다. 다만 정확한 NAT의 계층수는 알 수 없다. 추가적인 NAT의 존재 여부를 확인하기 위해서는 핫스팟의 셀룰러 측 주소 혹은 게이트웨이의 외부 주소를 외부에서 관측된 공인 주소와 비교하고, 상위 네트워크의 설정을 확인하는 등의 작업이 요구될 것이라고 생각한다.
- 핫스팟과 교내 네트워크를 비교하면, 로컬 IP 주소는 10.188.69.162에서 172.16.23.248로, 게이트워이는 10.188.69.73애소 172.16.23.1로, 공인 IP주소는 163.152.233.30에서 163.152.233.23으로 변경되었다. 반면 두 네트워크의 서브넷 마스크는 모두 /24로 동일하게 유지되었다. 로컬 주소의 변화는 서로 다른 DHCP 설정으로 설명이 가능하며, 서로 다른 네트워크에서도 동일한 크기의 서브넷을 사용하는 것이 가능했다. 두 공인 IP 주소가 서로  유사하다는 사실만으로 동일한 게이트웨이를 공유한다고 판단하는 것은 무리이며, 두 공인 주소 사이의 관계는 현재 확보 가능한 증거만으로는 설명되지 않는다.
- 핫스팟에서 캡처한 패킷에서는 프레임 2-5가 트랜잭션 ID 0x550b4a98을 사용하는 완전한 DORA 교환과정을 구성한다. DHCP Discover 메시지는 아직 IPv4 주소가 할당되지 않은 상태였기에 출발지 주소로 0.0.0.0을 사용했으며, DHCP 서버를 탐색하기 위해 목적지 주소로 255.255.255.255를 사용하였다. DHCP Offer에서 제안된 임대 시간은 3600초 였으며, DHCP ACK는 10.188.69.162로 유니캐스트 전송되었는데, 이는 서버가 클라이언트의 IP 주소와 하드웨어 주소를 알고 있고, 클라이언트가 유니새스크 패킷을 수신할 수 있는 경우 가능한 방식이다.

# Task 3

- 본인의 경우 경로를 프리픽스 길이 별로 딕셔너리에 그룹화하였다. 이 방식은 서로 다른 경로의 수를 N, 실제로 사용되는 프리픽시 길이의 수를 L이라고 할 때, O(N + L)의 저장공간을 사용하며, 비트 단위 트리 노드를 각각 생성하는 대신 딕셔너리 자체의 오버헤드를 사용한다. 새로운 프리픽스 길이가 추가될 때 마스크와 내림차순 탐색 순서를 미리 준비한다. 중복된 프리픽스가 존재하는 경우에는 첫 번째 next hop을 그대로 유지하되, 이는 LinearTable의 동작과 동일하다.
- 조회는 최대 L번의 마스킹된 딕셔너리 검색만 수행하며, N개의 경로를 모두 순차적으로 탐색하는 방식과 달리 기대 시간복잡도는 O(L)이다. 처음 발견되는 항목이 최장 프리픽스 일치가 된다. 기존 벤치마크 코드를 변경하지 않고 20,000개의 결과를 모두 확인했으며, 불일치는 0건 이었다. 이번 실행에서는 구진 구현이 16.875, 제 구현이 0.017초로 측정되여 ~1001.2배의 속도 향상을 보였다. 다만 실행 시간은 머선 환경과 실행 시점에 따라 달라질 수 있다. 전체의 출력결과는 bench.txt에 기록되어 있다.
- 비트 단위 트라이는 탐색 횟수가 일정한 범위 내로 제한되므로 전용 하드웨어에서 회로로 구현하기에 적합하다. 반면 Python에서 노드를 하나씩 순회하는 것은 인터프리터 실행 비용과 객체 접근 비용을 야기한다. 딕셔너리 조회는 최적회단 런타임 코드에서 수행되는 것이기 때문에, Python 환경에서는 더 효율적이다. 따라서 여기서는 딕셔너리를 사용하는 것이 합리적이며, 그렇다고 해서 모든 하드웨어 라우터가 동일한 자료 구조를 사용한다는 의미를 갖진 않는다.
