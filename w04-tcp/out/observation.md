# Task 1

- Stop-and-wait를 선택했다. 한 패킷씩 확인하므로 순서와 재전송 상태를 단순하게 관리할 수 있다. 특히 데이터는 도착했지만 ACK가 유실되는 경우를 처리하기 위해, 송신자는 10단계 후 재전송하고 수신자는 중복 데이터를 저장하지 않으면서 ACK를 다시 보낸다. 송신자는 현재 패킷 번호와 일치하는 ACK만 인정한다.
- 2,000바이트를 8바이트씩 나누므로 최소 데이터 패킷 수는 250개다. 검증 결과 seed 246에서는 데이터 전송 시도 323회(최소의 1.292배), seed 999에서는 299회(1.196배)였고 모두 IDENTICAL이었다. 이는 데이터 방향 채널의 sent 통계로, 유실된 전송 시도는 포함하고 ACK 전송과 채널이 생성한 복제본은 제외한다.
- 이번 검증에서는 손실·순서 변경·중복으로 인한 실패가 관찰되지 않아 무엇이 먼저 실패했다고 보고할 수는 없다. 손실은 타임아웃 재전송, 중복·뒤늦은 데이터는 순서 번호 검사와 재ACK, 오래된 ACK는 번호 검사로 처리했다. 추가로 100개 seed와 7개 길이(0, 1, 7, 8, 9, 2000, 2003)의 서로 다른 바이트 데이터 총 700개 사례에서 원본 일치 및 200,000단계 이내 종료를 확인했다.

# Task 2

- **캡처 분석(A2–A4):** `tcp.pcapng`의 `tcp.stream == 14`를 분석했다. 클라이언트 포트는 57087, 서버 포트는 443이며 SYN은 61번, SYN-ACK는 62번, 마지막 ACK는 63번이다. 실제 초기 시퀀스 번호(`tcp.seq_raw`)는 클라이언트 3836929649, 서버 1721221162다. Wireshark의 상대 번호 0과 달리 실제 ISN은 연결별 시퀀스 공간을 구분하고 오래된 세그먼트와의 혼동 및 번호 예측을 줄이기 위해 선택된다(0 자체가 금지된 값은 아니다). 클라이언트 SYN의 MSS는 1460, window scale 지수는 8(배율 256), SACK permitted는 활성화되어 있다. 서버 SYN-ACK는 MSS 1250, window scale 지수 13(배율 8192), SACK permitted 활성화다.
- **윈도우와 전송량(A5):** SYN의 윈도우에는 스케일을 적용하지 않는다. 연결 이후 클라이언트의 63번 패킷은 255 × 256 = 65,280바이트를 광고한다. 다운로드 중 서버의 최대 `tcp.analysis.bytes_in_flight`는 548번 패킷의 40,000바이트였다. 그 직전 클라이언트 윈도우 광고인 516번은 2047 × 256 = 524,032바이트이므로, 해당 시점의 전송 중 데이터는 수신 윈도우의 약 7.63%였다. 이는 수신 윈도우를 채워서 제한된 상황이 아니라는 근거다. 혼잡 윈도우/slow start, 경로 용량, 서버 전송 속도 등이 다른 제한 요인일 수 있지만 이 캡처만으로 하나를 확정할 수는 없다. Bytes in flight는 캡처에서 관찰한 추정치이며 송신자의 내부 혼잡 윈도우 자체가 아니다. `tcp_hotspot.pcapng`에서도 SYN/SYN-ACK를 확인했으며 추가 캡처로 보관했다.
- **처리량 비교(B3–B5):** `throughput.json`의 campus wifi 3세트(15회)를 모두 합산하고 mobile hotspot 1세트(5회)와 비교했다. 매회 다운로드는 5,000,000바이트이며 표의 변동 폭은 (최댓값−최솟값)/중앙값 × 100이다. 핫스팟은 핸드셰이크 중앙값이 약 6.78배 길고 처리량 중앙값은 캠퍼스의 약 16.88%였다. TCP slow start와 혼잡 회피는 ACK/RTT에 따라 윈도우가 성장하므로 RTT가 길면 증가 속도가 느려지고, 같은 전송 윈도우에서 가능한 처리량도 낮아질 수 있다. 무선 경쟁, 이동통신 스케줄링, 순간적인 큐 대기, 서버 응답 변동은 측정 편차의 가능한 원인이다. 이 코드의 처리량은 연결 수립 등을 포함한 전체 전송 시간 기준이므로 DNS·TLS·서버 응답 대기도 영향을 준다. 실제 원인별 기여도는 측정하지 않았으며 처리량 차이 전체를 RTT 탓으로 단정하지 않는다. 네트워크별 표본 수가 다르고 측정 시간도 달라 이 비교는 해당 실험 시점에 한정된다.

# Task 3

- ACK마다 window에 1/window를 더하고 손실마다 기존 값의 70%로 줄이는 AIMD를 구현했다(최소 1). 채널 내부 정보 없이 ACK와 손실에만 반응한다. 윈도우는 한 값으로 수렴하기보다 증가와 감소를 반복하며, 이번 실행에서 손실 직전 값은 약 23.7~32.0, 감소 직후는 약 16.6~22.4였다. 링크의 전파 지연에 해당하는 약 20패킷을 채우되, 그 이상은 큐를 늘리므로 손실 후 줄여야 한다. 시작부터 완만한 증가를 사용하고 별도의 slow start는 사용하지 않았다.
- 기준 송신자는 goodput 986.75/1000 slots로 더 높지만, 손실률 약 37.4%, 재전송 2340회, 평균 큐 약 8.8로 자원을 낭비하고 같은 큐를 사용하는 트래픽의 대기 시간을 늘린다. 구현 결과는 goodput 919.75(기준의 약 93.2%), 손실률 약 0.456%, 재전송 16회, 평균 큐 4.0875로 strong 조건을 만족했다. 공유 트래픽에 대한 영향은 큐 길이에 근거한 해석이며, 제공된 벤치마크는 송신자 하나만 시뮬레이션한다.
- 다른 조건을 유지하고 손실 후 유지 비율을 50%에서 70%로 높이자 goodput은 833.25에서 919.75로 증가했지만, 평균 큐는 2.85625에서 4.0875로, 손실률은 약 0.356%에서 0.456%로 증가했다. 80%에서는 goodput 939.75, 손실률 약 0.578%, 평균 큐 5.3035로 큐 제한을 초과했다. 따라서 처리량과 큐 지연의 균형을 위해 70%를 선택했다. 이 결과는 제공된 링크 조건에 대한 것이며 다른 링크에서도 같은 성능을 보장하지 않는다.
